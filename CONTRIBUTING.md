# Contributing to CSMP++

Thank you for contributing to CSMP++! We are grateful for all kinds of contributions ranging from fixing typos to bug fixes and new functionality.

This guide describes some general guidelines and our suggested workflow to contribute on GitHub. In short, all contributions come from forks, every change goes through a pull request (PR) into `main`, and every PR is reviewed before it is merged.

## General guidelines
Before walking through our git workflow, a few general guidelines:

### Reporting bugs
Like all software, CSMP++ includes bugs. It is of great help if you report bugs you may find via the `Issues` page on GitHub.

> [!WARNING]
> **Open Question:** Is the list complete?

When running into issues:
* Run your model in DEBUG mode, as this will provide more detailed information about the error and may already help you solve the issue. 
* Double check the `Issues` page for potential duplicate reports.
* If you did not find an answer, open a new issue and explain the problem in detail. Please attach:
	* information of the OS, compiler, and solver used
	* a configuration file and a simplified and small mesh that reproduces the issue (i.e., a minimal example)
	* the `*.log` file created during the run
	* the full error message output to the Terminal when running the model in DEBUG mode
	* instructions to reproduce the issue 
	* any additional information that may help to find a solution (e.g., has the code been modified before the issue occurred?)

This information is required for us to be able to try to help solve the issue.

## Our git workflow
### 1. Set up your fork (once)

Fork [`CSMPpp/CSMPpp`](https://github.com/CSMPpp/CSMPpp) on GitHub using the **Fork** button. Then clone your fork and add the main repository as a remote called `upstream`:

```bash
git clone git@github.com:<your-username>/CSMPpp.git
cd CSMPpp
git remote add upstream https://github.com/CSMPpp/CSMPpp.git
```

Your fork (`origin`) is where you push your branches; `upstream` is where you get the latest changes from. We do not push branches directly to the main repository.

### Optional: an additional remote for in-house development

If you develop new code in a repository at your institute (for example on GitLab) before contributing it to CSMP++, add that repository as a further remote:

```bash
git remote add institute git@gitlab.example.org:<group>/CSMPpp.git
git fetch institute
git remote -v            # should list origin, upstream and institute
```

A typical setup could be:

* **`upstream`** (GitHub, `CSMPpp/CSMPpp`): the official project. Read only access.
* **`origin`** (GitHub, your fork): where you push branches you want to contribute.
* **`institute`** (e.g., GitLab, GitHub, Bitbucket, ...): where you develop and share work in progress with colleagues.

Develop on a branch and push it to the institute repository as usual:

```bash
git fetch upstream
git checkout -b new-fracture-model upstream/main
# ... work, commit ...
git push institute new-fracture-model
```

Keep the institute repository's `main` in sync with the official project, so in-house work starts from the current code:

```bash
git fetch upstream
git checkout main
git merge --ff-only upstream/main
git push institute main
```

When the work is ready to contribute, bring the branch up to date with `upstream/main` (see step 4), push it to your GitHub fork, and open a PR from there:

```bash
git push origin new-fracture-model
```

Before contributing, make sure the code may be published and remove anything institute-specific such as local paths, specific configurations, personal information, or unpublished data.

### 2. Start each change from an up-to-date `main`

```bash
git fetch upstream
git checkout -b fix-gcc16-build-warnings upstream/main
```

Use one branch per change, with a short descriptive name. Keep each branch focused on a single topic, such as one bug fix, one feature, or one set of examples. If you notice an unrelated problem along the way, open a separate branch and PR for it. Small, focused PRs are reviewed faster and are easier to revert if needed.

### 3. Make the change, with tests

Add or update tests for what you change (if needed), and make sure the `ctest` test suite passes before committing and opening a PR.

Write commits with a short imperative summary line (for example, "Fix GCC16 build warnings"), a blank line, and a body explaining *why* when it is not obvious.

> [!WARNING]
> **Open Question:** Which tests need to pass? We cannot run all tests.

CSMP++ is used on Linux, macOS, and Windows. Avoid platform-specific code where possible, and mention in the PR which platforms and compilers you tested on. Fix new compiler warnings rather than leaving them.

### 4. Keep your branch up to date and push to your fork

If `main` has moved on while you were working, merge the latest `main` into your feature branch:

```bash
git fetch upstream
git checkout fix-gcc16-build-warnings
git merge upstream/main
```
> [!TIP]
> **Anne:** using git fetch + git merge could be replaced by git pull

Resolve any conflicts, rerun the tests, and push to your feature branch in your fork:

```bash
git push origin fix-gcc16-build-warnings
```

It is also good practice to keep your fork's `main` in sync with `upstream`, either with the **Sync fork** button on your fork's GitHub page or from the command line:

```bash
git checkout main
git merge --ff-only upstream/main
git push origin main
```

### 5. Open a pull request into `CSMPpp:main`

> [!TIP]
> **Anne:** Add template text that appears when people open up a PR. 
> This could for example list what people need to do, like describe what the PR does, apply the correct formatting, or have checkboxes to specify whether AI was used.


Open a PR only when the work is complete and all tests pass.

On GitHub, open a PR from `<your-username>:<branch>` into `CSMPpp:main`. Double-check the base branch before submitting. In the description:

* explain what the change does and why,
* link related issues (for example, `Fixes #57`),
* describe how you tested it (platforms, compilers, test cases),
* point out anything reviewers should look at closely.

Leave **Allow edits by maintainers** checked, so reviewers can push small fixes to your branch.

### 6. Review

At least one maintainer needs to review and approve a PR before it can be merged.

**Reviewers** collect their comments into a single review, mark which points block the merge and which are optional (for example with the prefixes **Blocking:**, **Suggestion:**, **Nit:**, **Question:**), use suggestion blocks for small concrete fixes, and finish with **Approve** or **Request changes** together with a short summary.

**Authors** respond to each comment thread and push fixes as new commits to the same branch, so reviewers can see exactly what changed since their last review. Reviewers resolve the threads once they are satisfied. Disagreements are discussed in the thread rather than ignored.

### 7. Merge

Once the checks pass and the PR is approved, a maintainer merges it. The default is **Squash and merge**: one commit per PR on `main`, with

* the PR title as the summary line (GitHub appends the PR number), and
* a cleaned-up PR description as the body, without checklists, screenshots, or review discussion.

**Rebase and merge** is used only when each commit is meaningful on its own and passes the tests.

### 8. Clean up

After your PR is merged, delete the branch in your fork (GitHub offers a **Delete branch** button on the merged PR), then update your local `main` and remove the local branch:

```bash
git checkout main
git fetch upstream
git merge --ff-only upstream/main
git push origin main                    # update your GitHub fork
git branch -d fix-gcc16-build-warnings  # delete your local branch
```
> [!TIP]
> **Anne:** using git fetch + git merge could be replaced by git pull


If git reports that the branch is not fully merged (common after a squash merge), use `git branch -D` once you’ve confirmed the PR was merged.

If you also pushed the branch to an institute repository, delete it there too and update `main`:

```bash
git push institute main                              # update the institute repository
git push institute --delete fix-gcc16-build-warnings # delete branch on the institute repository
```
