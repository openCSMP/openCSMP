22@brief Permforms node-by-node computations of aqueous - solid phase equilibria
23using the ODE_StiffSolver in a reaction based aproach.
24
25@class AlterationVisitor AlterationVisitor "visitors/AlterationVisitor.h"
26@author S.K. Matthaei
27@author S. Geiger
28@date 1999
29
30@section motivation Motivation
31
32
33In order to carry out rate-dependent reaction calculations, one needs
34to visit the nodes or elements of the finite-element mesh, retrieve
35aqueous species concentrations (moles m-3) and mineral fractions (X),
36respectively, carry out speciation calculation for the alloted time
37increment, and map the results back to the Model.
38
39Since full equilibrium calculations are meaningful only for
40fracture-channelled flow and its interaction with the matrix but not for
41matrix flow where disequilibrium may persist between pore fluid and matrix
42minerals, the scheme should also allow rate-dependent calculations.
43
44The scheme should be simple. This is achieved by the SNIA approach.
45
46
47@section design Design Intent
48
49Encapsulation appears critical in order to deal accurately with the
50complexity of the aqueous systems. It is achieved by delegating
51the numerics of the equilibration calculation to a solver object
52for stiff systems of ordinary differential equations. Critical properties
53of aqueous solutes, minerals, and gases are encapsulated into
54Reactant objects.
55
56Zero-dimensional reaction calculations can be carried out outside of
57a more complex CSP-reactive-transport model. This is the method of choice
58for designing and testing chemical systems before looking at their spatial
59implications by means of a CSP model. Design and testing is done
60by iteratively creating and modifying a reaction file which is used
61to initialize the solver for ordinary differential equations, both inside
62and outside of CSP. The design-proofed text file is then read by the
63AlterationVisitor to initialize the reaction calculations. In this
64approach, the dependent variables defined in the input file must
65also be known to the PropertyDatabase. Hence, they must be incorporated
66into the 'CSP_variables.txt' file. In addition to the reactions file
67the constructor of the AlterationVisitor also expects a datafile
68which lists the reactants again, specifying their phase state (solid, aqueous,
69gas) charge, density, and molar weight, as applicable. This file is
70read after the ODE solver is initialized and it is tested for a
71mismatch of species names.
72
73Robustness is quint-essential since an inability of the A.V. to treat
74the chemical system at just a single node would bring the whole reactive
75transport model to a halt. This goal is achieved only partly.
76Importantly, as is documented in more detail for the 'ODE_StiffSolver'
77object, rate coefficients in a single system may not vary by more than
78about 12 orders of magnitude among the different dependent variables.
79Otherwise a solution cannot be assured, while a calculation may still
80perform correctly in most cases. Usually, a large number of bad
81steps taken by the ODE solver is an indication that a chemical
82system is problematic.
83
84Flexibility is dictated by the need to iteratively refine the aqueous
85system calculation and to test the functionality of such refinements for
86the modeled geological system of interest. To achieve this goal,
87hardcoding of reactant names is avoided except for the variable H2O_aq
88which must be present and which is also used to decide whether a
89chemical calculation is carried out or not: If the variable H2O_aq
90is flagged DIRICH, chemical calculations are prohibited at the respective
91Node.
92
93Apart from the variable "H2O_aq" some physical properties are also
94hardwired since they are likely to be needed for every conceivable reactive
95transport calculation.Their names are
96
97@code
98"nodal porosity"
99"fluid density"
100"rock density"
101"nodal fluid source"
102"H2O_aq"
103@endcode
104
105They must be specified in the "CSP_variables.txt" file if the
106AlterationVisitor object shall be used.
107
108Efficiency of the AlterationVisitor is very important since calls
109to its Visit() method usually prove to be the main time sink of a
110transient CSP calculation (worse than advection requirements). The
111main culprit in terms of runtime is the ODE_StiffSolver::Solve()
112method. For this reason, the invocation of the solver is limited
113to scenarios where, either, the absolute concentration / volume
114fraction of a mineral has changed by a user-specified factor.
115This factor can be set with the method 'ThresholdReactantChangeFactor()',
116An additional criterion is whether equilibration was obtained in the
117previous timestep. The latter is indicated by the rates of change
118of the reactants in the final finite-difference timestep taken by the
119solver during the last visitation of the node. Again, a threshold rate
120above which the solver will be invoked can be set using the method
121'ThresholdReactantChangeRate()'.
122
123
124@section applicability Applicability
125
126This specific implementation of the AlterationVisitor is suitable for
127arbitrary chemical calculations in which the reactants are specified as
128CSP node variables.

148@section implementation Implementation
149
150Each visitation involves reading nodal properties from the Model
151storage (1), a conversion of these mineral fractions and concentrations
152per unit volume (m3) into molalities (2), an invocation of the ODE solver if
153reactant concentrations / fractions changed above a tolerance value
154since the last visitation or if the previous rate of change was still high
155(4). The computed molalities are converted back into concentrations and
156fractions and stored back into the Model (5). From these results,
157a new porosity and rock density is calculated (6), and a potential
158"nodal fluid source" term is computed and stored (7). Finally,
159the absolute reactant quantities and reaction rates for each dependent
160variable are stored as solver invocation criteria for the next timestep (8).
161
162The results of each visitation can be output if the visitor is set
163to verbose mode. This is done using the second argument of the
164Equilibrate() method and is the default.
165
166
167@section examples Application Examples
168
169An AlterationVisitor is instantiated after a Model was constructed:
170
171@code
172 AlterationVisitor reactor( sg_model, "rea-file1", time_increment );
173@endcode
174
175and is applied, for instance in a time-stepping loop by calling:
176
177@code
178 reactor.Equilibrate( model, false );
179@endcode
180
181In this example the verbose output of each speciation calculation
182is disabled by setting the second 'boolean' argument.
183
