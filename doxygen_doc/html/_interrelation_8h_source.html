63@section motivation Motivation
64
65Traditionally, locally resolvable interdependencies of dependent model
66variables are computed in so-called 'post-processing' operations which
67involve looping through arrays of nodes and elements, applying mathematical
68relationships to compute the variable(s) of interest. This procedure is
69error prone, firstly, because of the danger of writing beyond array
70bounds which the top level user is not necessarily familiar with;
71secondly, the results of such calculations are not tested before they are
72written into the global arrays; and, thirdly, if one has many of such
73calculation procedures inside of a time-stepping loop, it becomes hard
74to track which post-processing procedure depends on a previous one,
75to determine an execution order which must be adhered to.
76
77The Interrelation class represents an attempt to overcome these dangers
78by encapsulating post-processing operations into modules. This design
79achieves the following objectives:
80
81Firstly, the loop operations and variable access is embedded into
82the Interrelation class. The user must only associate an Operand
83object with the variable which he can subsequently use in
84the mathematical expressions.
85
86Secondly, The result of such a calculation is tested before it is
87stored back into the MemoryManager. This test determines whether
88the result lies in a physically meaningful range for which other
89Interrelations that use the variable as an input, have been tested
90(This is essential to ascertain the correctness of a complex
91simulation).
92
93Thirdly, Interrelations always modify only a single variable. This
94restriction allows them to be managed by an InterrelationManager
95which automatically determines an Interrelation computation
96sequence in time-stepping loops.
97
98There is also a need to used node variables in the computation of
99element properties and so forth. For these type of calculations, the
100Interrelation class has the capability of taking property averages
101or apply other useful strategies through the use of Operand
102objects.
103
104
105
106@section design Design Intent
107
108
109In the CSMP modeling code, all calculations that do not involve the
110inversion of a global solution matrix are done by passing
111Interrelation subclass instances to Model objects. An example of
112an Interrelation would be the calculation of the hydraulic conductivity
113from the permeability by dividing permeability by viscosity and assigning
114the result to the variable conductivity. The code that does this is
115provided as the class 'ConductivityFromPerm' as defined in a header file
116with the same name.
117
118
119@section applicability Applicability
120
121
122All calculations in a CSP model which can be done in an element by element
123fashion or just by looking at node or constraint point variables only,
124should be encapsulated into Interrelations. Exceptions from this rule
125are global expressions which one may want to write using PropertyHandle
126objects. Also, for the special case where a well-understood process
127modifies several variables simultaneously, which would require multiple
128interrelations, a visitor object may be better suited to achieve the
129computation goal.
130
131Importantly, Interrelations can be restricted such that they apply
132only to subregions of a model identified as Region objects. This
133capability allows, for instance, to compute a magmatic fluid source
134within a cooling granite without the overhead of traversing the
135entire mesh.
136
137
138@section structure Structure
139
140
141The Interrelation class is a base class from which the user inherits
142a subclass object for instance 'ConductivityFromPerm' which
143contains the mathematical expression which the user wants to apply.
144Inheriting such a subclass involves the following steps:
145
146Firstly, the user must define a notation for his mathematical expression
147by associating a Operand objects with the global physical variables of
148interest (for the above example):
149
150@code
151class ConductivityFromPerm : public Interrelation {
152Operand& K; // hydraulic conductivity
153Operand& k; // permeability
154Operand& V; // dynamic viscosity
155...
156@endcode
157
158Secondly, the user must register the variables with the Model,
159define a name of the Interrelation, the output property, and the write
160permission flag. This is done in the constructor of the Interrelation
161subclass:
162
163@code
164ConductivityFromPerm::ConductivityFromPerm( const Property& p )
165 : Interrelation(p),
166 k( GlobalProperty("permeability") ),
167 K( GlobalProperty("conductivity") ),
168 V( GlobalProperty("viscosity") )
169 {
170 Name(" ConductivityFromPerm");
171 ResultProperty("conductivity");
172 OutputConditions( K, PLAIN );
173 }
174 @endcode
175
176k, K, and V are associated with the global physical variables
177identified by their spelled out name, 'conductivity' is defined as
178the property which will be modified by the Interrelation, but only
179where it has the flag PLAIN.
180
181Thirdly, the user must overwrite the pure virtual method Calculate()
182of the Interrelation base class, defining the mathematical expression
183he wants to apply n order to compute the target variable:
184
185@code
186inline void ConductivityFromPerm::Calculate()
187 {
188 K = 1.0 / viscosity;
189 K *= k;
190 }
191@endcode
192
193Here Calculate() is defined as a C++ inline function (to reduce
194computation overhead), which first assigns 1/viscosity to the
195global physical variable conductivity. Then the latter is
196multiplied by the permeability according to Darcy's law:
197
198K = k/v
199
200Please refer to the documentation of the Operand class to see
201how to write mathematical expressions involving Operand objects.
202
203
204@section participant Participants
205
206An Interrelation object always contains Operands and a reference to the
207PropertyDatabase in order to register and manage the physical variables.
208
209
210@section collaborations Collaborations
211
212The Interrelation collaborates with Model and Region objects in
213order to compute the desired properties. To apply an Interrelation to
214a model just submitt it to the Model:
215
216ConductivityFromPerm my_interrelation( var_database_reference );
217model.Apply( my_interrelation );

221@section consequences Consequences
222
223To make use of the Interrelation capability of CSP one must define and
224compile Interrelation subclasses. A small library of these is provided
225but the intend is to build a large moderated internet repository of
226Interrelation objects from which all CSP users can profit and to which
227they can submit their own Interrelation subclasses.
228

230@section implementation Implementation
231
232
233The Interrelation uses a conditional loop within its Apply() interface
234to establish the input values for each calculation. It tests the
235calculation results with ResultWithinRange(), before these are
236communicated back to the Model object.
237
238If an interrelation subclass involves scalar, vector, and/or tensor
239variables simultaneously, you can access these variables directly
240by using the AssignTo() method of the Operand class. This allows you
241to make use of the rich interfaces of the Scalar-, Vector-, and
242TensorVariable classes.

245@section examples Application Examples
246
247As already discussed above, one must define and compile Interrelation
248subclasses to make use of the Interrelation capability of CSP. The steps
249involved in this process are described in more detail below:
250
251 1. Test the interrelation among variables that you would like to express.
252 This may involve graphing and designing the Interrelation in matlab or
253 Mathematica or doing a curve fit through some experimental data within
254 Excel. You will also have to identify the value range for each of the
255 involved variables. Within this value range your mathematical
256 formulation must produce meaningful results. This value range should be
257 at least as wide as the value range that you specified in the variable
258 database text file from which the programm initializes its variable
259 storage. This is extremely important since it is the only way of
260 ascertaining that the CSP code produces correct results once your model
261 becomes complex and contains several interrelations.
262
263
264 2. Define your notation and make each symbol a reference to an
265 Operand object. These references should
266 be private data members of your subclass which you define through public
267 derivation from the Interrelation class. Importantly, if you don't make
268 Operands references, you will create new variables and your calculation will
269 either not read any of the variable values stored in the Model
270 object, or your calculation result will not be transmitted back into
271 the Model.
272
273 3. Register your variables in the constructor of your derived class. In
274 C++ all references must be initialized in the constructor. First, you
275 construct the base class, then you use the base class method
276 GlobalProperty() to register the involved variables and finally you
277 define which of these variables will store the result of your
278 calculation. This is done with the base class method
279 DefineResultProperty(). You also have to provide the Interrelation
280 with output conditions (use method OutputConditions().
281 The use of these conditions is to prevent the Interrelation from
282 overwriting variable values that you have fixed (e.g. DIRICH conditions)
283 or to read variables that have not yet a meaningful value.
284
285 4. Define your own version of the pure virtual member function
286 Calculate() of the Interrelation base class. This method will contain
287 your mathematical formulation of the interrelation written using a
288 normal notation involving * / + - < > <= >= and other mathematical
289 operations as are
290 defined as overloaded operators of the Operand class. Avoid the
291 construction of too many temporaries within this method. If you need
292 many, make them static such that they do not get destructed when the
293 method goes out of scope. Also, if you write something like:
294
295 K += b + c - d * 24.5;
296
297 you will automatically create a 4 temporary Operands (why ? - make this
298 a little exercise).
299
300 5. Decide where to apply your Interrelation and pass it to the
301 Model which will call the Interrelation method Apply(), that
302 performs a range check on the values that your calculation produces.
303
304 6. You have to define the application domain, if you want to have your
305 interrelation applied only to a group of elements rather than the
306 Model. Use the method RestrictApplicationTo() to achieve this.
307
308The calculations that you can perform with Interrelation
309subclasses are limited. You can only calculate result variables that
310are on the same or a higher level in the Model storage hierarchy. For
311instance you can calculate an element property from node, or constraint point
312property, but not the other way around. Use a visitor and the Parent references
313of the Node or IntegrationPoint classes to do this. Also if you calculate an element
314property from node property values, the interrelation will use an
315average over the nodes rather than individual values in the calculation.
316If this is too limiting for you than you can overrule the baseclass methods
317with your own method. Before you do that, however, consider to do
318your calculation as postprocessng operations of an Algorithm or via
319a Visitor object.
320
321@todo (1) Remove interrelations after porting functionality to PropertyHandle and visitors (A)
