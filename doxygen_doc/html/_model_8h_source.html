33/**
34@brief Model the playground for the physics of interest
35
36@author S.K. Matthai
37@author Stephen G. Roberts
38@date 1999
39
40@section motivation Motivation
41
42Finite-element models typically are characterized by arrays
43of data that need to be accessed via complex indexing operations and whose
44interconnectedness is not explicit. Also it is relatively error
45prone to change the size of these arrays at runtime and to update the
46connectivity of represented finite elements. Tohe design of the Model
47class was therefore motivated by the need to hide this complexity from the
48user such that he/she can focus their undivided attention on the geological
49complexity of the problem at hand.
50
51
52@section design Design Intent
53
54The design intent was to have an object representation
55of the mass and space occupancy of a real world system of interest.
56One should be able to work with and observe this system through the interfaces
57of the Model object.
58
59
60@section applicability Applicability
61
62A Model representation can be built for any geometrical model which
63represents a finite-element discretization of a real-world system.
64Computations on a Model are carried out through its interface Apply().
65Through this interface you can carry out finite-element computations
66specified by Algorithms or own types derived from the classes Algorithm,
67and 'Algorithm'. You can also calculate interrelations among variables
68(including the dependent variables that are computed at each timestep).
69You do this with your own classes that you derive from the Interrelation
70base class. An example for such an Interrelation-derived calculation would
71be to calculate a permeability that is dependent on fluid pressure. Any
72derived algorithm or interrelation can also be restricted to Regions of
73Elements inside the Model.
74
75
76@section structure Structure
77
78The Model is an agglomerate of objects representing the finite-element mesh,
79implemented as a connectivity scheme and a storage scheme for physical
80variables that are assigned to nodes, constraint points, or elements
81themselves. Regions of elements that make up geological entities in the
82model are referred to as Region objects.
83
84The Model contains a class hierarchy of Region, Element, IntegrationPoint,
85and Node objects. Their connections reflect the connectivity of the mesh and
86they are handled internally by the MeshManager. The complementary
87MemoryManager object manages the storage for the distributed physical
88variables of a computation. The PropertyDatabase object keeps track of the
89existing properties, their storage locations and specifications.
90
91
92@section participants Participants
93
94The Model functionality is instrumentalized through instances of Node,
95IntegrationPoint, and Element classes managed by the MeshManager;
96basic CSMP variables managed by the MemoryManager;
97a PropertyDatabase, and a map of Regions.
98
99
100@section collaborations Collaborations
101
102In a typical CSMP simulation, the Model collaborates with Algorithm,
103Interrelation, and Visitor objects via its Apply() and Accept() interfaces,
104respectively. For data transfer, the Model can also exchange properties
105with a FiniteDifferenceGrid object using the Element interpolation functions.
106
107
108@section consequences Consequences
109
110A Model encapsulates the discretization of a geological object with
111associated properties. It thereby creates an interface to this object which
112allows to carry out computations on the object, modify property values,
113input and output these to other tools, and to address and manipulate sub-
114regions of the object. Sub-regions can be identified on the
115basis of property values and they can be associated with a name. Once this
116is done, most of the Model interface can also be used for
117individual Regions.
118
119
120@section implementation Implementation
121
122The public interfaces of the Model invoke a data-access process for
123the discretized real-world model. The key steps in this process are:
124
125(1) The Property Database is queried for the
126variable specifications of a variable defined as an input string (for
127instance "permeability"). The database returns a csmp::Index that uniquely
128identifies the variable for efficient access in the computations.
129
130(2) The placement of the variable (Node, IntegrationPoint or Element)
131determines the depth of the search for the variable in the hierarchy of the
132mesh in the Model object.
133
134(3) Once a variable location object (Node, IntegrationPoint, or Element)
135is found, its ID is used to retrieve the value or status of the variable from the
136MemoryManager via methods like Read() or Store(). These methods are
137overloaded to retrieve Scalar-, Vector-, and TensorVariable<dim> instances.
138
139(4) Within the MemoryManager object the variables live in
140STL vectors that were instantiated for the specific variable types. The length
141of such vectors depends on the placement of the variables. Originally the
142MemoryManager object is build for the variables that were specified in
143the variable database from your input file. When you create a new variable at
144runtime (using PropertyHandle objects), a new vector is build and inserted
145for this variable. The addresses of other variables remain valid in
146this process. Thus, you can efficiently create new variables at runtime.
147
148
149@section examples Application Examples
150
151In the following example, the element type LinearTriangle is set as
152default finite-element. A Triangulator mesh generator object is used by
153the Model constructor to generate a mesh of triangular finite-elements.
154This mesh is build from regular-gridded input data for which the user is
155prompted and the mesh in used further to buid a Model object named
156'model'. In this process, the default variable text file 'CSP_variables.txt'
157is read to initialize the variable database. The porosity of the new model is
158set to a uniform value of 3% and DIRICH(let) boundary conditions are applied
159at the model top (cross-sectional model). Now, instances of subclasses of
160Algorithms, Interrelations and Visitors are applied by 'passing' them
161to the Model. This invokes global (mesh-wide) and local (finite-element
162restricted) computations. Finally the variable 'temperature' is output
163to the HDF file 'computed_temperature'.
164
165
166@code
167Triangulator mesher;
168
169Model model( "CM-simulation", mesher );
170
171model.InputUniformValueWhere ( PLAIN, "porosity", 0.03 );
172
173model.AssignBoundaryValues( TOP, "temperature", DIRICH, top_T, top_T );
174
175model.Apply( interrelation_subclass );
176
177model.Apply( csp_algorithm_subclass );
178
179model.OutputDataToHDF ( "computed_temperature", "temperature" );
180@endcode
181
182

186*/
