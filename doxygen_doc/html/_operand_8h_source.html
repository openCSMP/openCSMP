16@brief Interface for all of CSMP's variable types facilitating that they
17can be used together in computations; currently used only by Interrelation; outdated design, refactoring required.
18
19@author S.K. Matthai
20@author Stephen G. Roberts
21@date 1999
22
23@section motivation Motivation
24
25Forget for a moment all about the rest of the CSMP code except for the basic
26variables ScalarVariable, VectorVariable and TensorVariable and think of
27the possibility of creating objects that are overloaded such that you can
28write expressions for the whole mesh object or sub-regions thereof, which
29read like mathematical equations in which the variables refer to local
30or distributed data.
31
32This quest was the design intent of the Operand class and it brings CSP
33users close to this goal when they are prepared to write their own
34Interrelation subclasses. The goal is fully realized through the new
35PropertyHandle classes for use in main() programs. These are however only
36complementary to the Operand and Interrelation mechanism, because they
37do not encapsulate the calculations which Interrelations do.
38
39
40@section design Design Intent
41
42Apart from being able to write mathematical expressions which are applied to
43the whole Model or sub-Regions thereof (as is facilitated through
44the PropertyHandle class), there is a need to use distributed instances of
45properties in calculations inside objects which are still efficient and
46allow the user to partially ignore variable IDs and the variable placement
47in the mesh (Node, IntegrationPoint or Element). This requires (1) the use
48of a notation to represent the variable in mathematical expressions,
49and (2) an association of the csmp::Index of the variable with the notation such
50that it does not need to be requested from the PropertyDatabase every time
51the expression is evaluated. Finally (3), temporary variable storage is
52needed to allow that a value can be range-checked before
53it is written back into the Model storage. This buffer is essential
54when it comes to checking where in a chain of expressions, a physically
55meaningless value was produced.
56
57
58@section applicability Applicability
59
60Operands are used in Interrelations, Algorithms, Algorithms, and
61Visitor objects.
62
63
64@section structure Structure
65
66The Operand is a simple class object with a String containing its
67name, a csmp::Index describing the represented variable, and
68each one of the basic CSMP variables as well as an output condition
69flag which specifies the VARIABLE_FLAG of the property locations which
70the variable is permitted to overwrite if the calculation yielded a
71result which is within the permitted range.
72
73@section participants Participants
74
75A csmp::Index, a String, an output VARIABLE_FLAG and CSP basic variables
76(ScalarVariable, VectorVariable, and TensorVariable).
77
78
79@section collaborations Collaborations
80
81Operands collaborate with CSP basic variables and the
82enumerations which are defined in CSMP_definitions.h (e.g., VARIABLE_FLAG...).
83

85@section consequences Consequences
86
87
88The operators \f$+, -, *, /, +=, -=, *=, /= \f$ are overloaded for Operands such
89that they can interact with eachother, double data, and the CSP basic
90variables. One should not write expressions like A = C. Following the logic
91of an assignment, A = B means: The Operand A now
92refers to exactly the same variable as B and it will also contain the same
93values. If Operand A represents a property stored in the Model, the
94variable A will no longer exist following the assignment.
95
96Importantly, scalar-, vector-, and tensor variables are more than
97just mathematical variables in that they also contain a STATUS flag which
98specifies how they are treated in the assembly of the finite-element
99equations. This requires some rules about the flag assignment: If you say
100
101@code
102A = C + B;
103@endcode
104
105the temporary variable that is created will be flagged like the lefthand
106operator before the assigment. If \f$C = PLAIN\f$ and \f$B=DIRICH\f$, A will be
107\f$PLAIN\f$. If the combined operator += is used, A will retain its original flag
108because the assignment here uses the assignment as defined for scalar
109variables.
110
111If you compare an Operand with a VARIABLE_FLAG enumeration, the comparison
112will be carried out using all flag(s) of the underlying variable. Thus,
113if a vector variable in a 2D calculation has two different flags (for instance,
114a DIRICH flag for the X displacement and a PLAIN flag for the Y displacement)
115a comparison will evaluate as false. In this case one should use
116VectorVariable::Flag( int i) to carry out a more specific comparison.
117Any comparisons with not initialized Operands or Operands that
118store NAN values in the variables will evaluate as false.
119
120
121@section implementation Implementation
122
123By default, Operands have storage for a single variable value of type
124ScalarVariable, VectorVariable, or TensorVariable, but only if this variable
125exists in the PropertyDatabase (in contrast, PropertyHandles spawn the
126generation of a new variable in the PropertyDatabase if the variable does
127not exist).
128
129The need for large computations imposes stringend constraints on the properties
130of Operands. They may be big in size because there will only be a few, but their
131overloaded operators have to be efficient since single calculations may involve
132millions of calls to those. Already a function call overhead is significant for
133the overloaded operators. To avoid this overhead auto-inlining is used in the
134compilation.
135
136The construction of temporary 'Operands' in expressions like:
137
138@code
139C = A + 32.5;
140@endcode
141
142should also be avoided. In those cases the construction by the compiler
143of temporary objects (object x which will be assigned to C) can be avoided
144only in some cases through construction of the Operands in the return
145statements of the overloaded operators.
146
147To avoid the creation of temporaries you should rather write:
148
149@code
150C = 32.5;\
151C += A;
152@endcode
153
154Operands also store a 'calculation offset' which is used by Algorithms
155to modify the placement of dependent variables in computations
156involving the Operand variable, when coupled systems of equations
157are solved.
158
159
160@section application Application Examples
161
162
163Operands are typically used in Algorithms and Interrelations. When you
164derive a subclass from an Interrelation, you first create a Operand
165reference to a physical variable in your model:
166
167@code
168Operand& K;
169@endcode
170
171You then associate the Operand with a property which has been defined
172before as a member of the PropertyDatabase. This happens in your
173interrelation constructor.
174
175@code
176K( GlobalProperty("conductivity") )
177@endcode
178
179This defines K as a notation for 'conductivity'. You can
180now use K in expressions using CSMP basic variables and other Operands:
181
182@code
183K += PHI / 322.1 - 45.0;
184@endcode
