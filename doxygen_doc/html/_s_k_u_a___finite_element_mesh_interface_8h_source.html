15
16@brief File based interface between SKUA and CSMP.
17
18To provide a direct file-based interface between the SKUA's FiniteElementMesher and CSMP,
19allowing to read parts of the input mesh selectively, assign material properties, boundary conditions
20and to rigorously test the incorporated mesh for its compliance with
21CSMP requirements.
22
23@author S.K. Matthai
24@author Thomas Jerome
25@date 2020
26
27@section participants Participants
28
29Part of the file format of this interface is modelled on the SKUA interface using the classes VSet, FEM_Primitive and
30ModelTopology to store the information retrieved from file.
31
32
33@section implementation Implementation
34
35Two files: one human readable text (.asc = ASCII) file and a binary (.dat) file
36that can be transferred across platforms (Windows OSX, linux etc/).
37Both files have the same name (model name) and are distinguished only by their extension.
38
39The regions and material file ('*.asc'):
40
41- model name (line break)
42
43- Comment line (header): 1. filename, 2. date of generaton
44
45- Number of labelled objects
46
47- Table with objects, element types, material ID values (rock types), number of elements (cells)
48
49@code
50 Object element-type material ID number-of-elements
51 LIV TETRA_4 3 760
52 BOXS TRI_3 0 2030
53 CURVES BAR_2 0 20
54@endcode
55
56The material ID facilitates the association of 'rock types' with model regions.
57
58- List of elements making up each region (numbered 0...n-1), preceded by region name and
59number of elements of region.
60
61@code
62 UNIT_1 6
63 12 13 14 15 16 17
64@endcode
65
66The binary file ('*.dat') contains:
67
681. NODE COORDINATE DATA (double):
69
70PX, PY, PZ records: preceded by a single unsigned long indicating the size of
71these records which (individually) contain (with or without line breaks):
72
73px: -> x-coordinates of the nodes
74py: -> y-coordinates of the nodes
75pz: -> z-coordinates of the nodes
76
77(all entries in these records have the format double and
78the node-IDs are implicit from 0 to nodes-1):
79
80Such records could be written as shown in the C++ code example
81below:
82
83@code
84double* ptr; // data pointer
85...
86unsigned long n0(0), n1(1);
87
88if ( (records=px.size()) > 0 && (ptr=const_cast<double*>(px.Data())) != NULL )
89 {
90 fwrite( (void*) &records, sizeof(unsigned long), 1, fp );
91 fwrite( (void*) ptr, sizeof(double), records, fp );
92 }
93else fwrite( (void*) &n0, sizeof(unsigned long), 1, fp );
94@endcode
95
962. NODE FLAGS (int)
97
98PBFLAGS: Same record length as the record set above but in int32_t format.
99
100- if a node lies on a model boundary, a negative integer value
101 is assigned to identify that boundary uniquely in terms of the
102 named surface it belongs to. If the node is not located on a
103 model boundary, its int value is set to zero. If lines or curves were
104 specified on the model boundaries, edge nodes along these lines are
105 flagged by unique negative integers by analogy to the identifiers for
106 the edges in the SKUA topology.
107
108 A boundary and edge numbering scheme for box-shaped models in CSP has
109 the following values (adhering to a righthand-rule coordinate system
110 where x points to the right, y points upward and z points to the front:
111
112@code
113#define BACK_BOTTOM -16 // BACK and BOTTOM
114#define BACK_RIGHT -17 // BACK and RIGHT
115#define BACK_TOP -18 // BACK and TOP
116#define BACK_LEFT -19 // BACK and LEFT
117#define BOTTOM_RIGHT -20 // BOTTOM and RIGHT
118#define TOP_RIGHT -21 // TOP and RIGHT
119#define TOP_LEFT -22 // TOP and LEFT
120#define BOTTOM_LEFT -23 // BOTTOM and LEFT
121#define FRONT_BOTTOM -24 // FRONT and BOTTOM
122#define FRONT_RIGHT -25 // FRONT and RIGHT
123#define FRONT_TOP -26 // FRONT and TOP
124#define FRONT_LEFT -27 // FRONT and LEFT
125@endcode
126
127
1283. BOUNDARY CONDITIONS APPLIED TO NODES (double)
129
130PBVALS: Analogous to the record sets above but in double format:
131
132- Corresponding to the non-zero flags from above, where a node is
133 located at a model boundary, a boundary value as previously assigned
134 to the SKUA topological model can be stored in this data record.
135 If no value was assigned, this record will just hold zeroes.
136
137
1384. TYPE OF FINITE ELEMENTS (enum -> unsigned int)
139
140PELMT (0...e-1): Record is preceded by an unsigned long indicating
141record size (=number of finite elements in the mesh). 'pelmt'
142consists of a single record of (all as unsigned longs):
143
144- element-type identifiers (unsigned int) for each
145 finite element in the mesh. How they correspond to element
146 type strings is specified further below.
147
148 Dieser Eintrag vermeidet Doppeldeutigkeiten, die dadurch entstehen
149 koennten, dass es verschiedene Elementtypen mit der gleichen Anzahl
150 von Knotenpunkten gibt.
151
152
1535. MESH CONNECTIVITY (unsigned long)
154
155PLIST: Record preceded by an unsigned long indicating record size,
156a single record follows containing (all as unsigned longs):
157
158- node ids of each element in
159 counter-clockwise order (according to node numbering on reference elements).
160 The enlisted node numbers range from 0...nodes-1 as above.
161
162The elements are numbered implicitly and continuously by their position
163in the plist (there must be no jumps in the element ids).
164
165
166PFVERTS: Record preceded by unsigned long indicating record size, then a
167single record (all long, where negative numbers denote model boundaries):
168
169- neighbour elements
170 of each element in an order defined for each existing element
171 type (see further below, for tetrahedra and triangles, neighbors are
172 those elements touching the element's faces opposite of its corner nodes).
173 Neighbor elements are denoted 0...element-1. Where there are no neighbour
174 elements adjacent to the element's faces because the element lies on a model
175 boundary, a negative long is used to identify this boundary surface.
176
177
1786. MATERIAL IDENTIFIER FOR EACH ELEMENT = ROCK TYPE
179
180PMTRL: preceded by number of elements, associates each element with the
181material flag from the '*.asc' file such that properties can be assigned.
182
183Comments: leading hash key (# everything thereafter is ignored)
184
185
1867. ELEMENT AND NODE PROPERTIES
187
188Following the material ID record of integers, the property data block starts.
189Since the properties have different placements (element, node etc.) and types (scalar, vector, tensor, array, flagged-array),
190this information must be specified alongside with the property name.
191Furthermore, by contrast with VectorVariable (dim) and TensorVariable (dim x dim), the size of which is defined by the model dimension, dim,
192ArrayVariable and FlaggedArrayVariable have a length (number of entries) that is defined at runtime
193and therefore has to be specified.
194While each ArrayVariable has only one flag, each FlaggedArrayVariable has one flag per value.
195For this reason, flag strides and data strides are provided for all variables.
196
197In summary, a complete record for a CSMP variable consists of:
198
199name(string) placement(enum PLACEMENT) type (VARIABLE_TYPE) (array length (int32))
200number of data entries (int32)
201flag values (int32)
202property values (double)
203
204Since the names can contain whitespace, they are placed in quotation marks.
205
