\subsubsection*{template$<$uint32\+\_\+t dim$>$\newline
class csmp\+::\+Element$<$ dim $>$}
Object representation of a finite element Bridge pattern together with \doxylink{classcsmp_1_1_finite_element}{Finite\+Element} class.

\hypertarget{compare_floats_8h_motivation}{}\doxysubsection{\texorpdfstring{Motivation}{Motivation}}\label{compare_floats_8h_motivation}
The finite-\/element method uses areal/volumetric elements as smallest computational units. Each element has 2 functions\+: (1) to store material properties and nodes with associated properties; (2) To generate matrices which contribute to a global system of algebraic equations which is solved to obtain the value of the dependent spatially-\/distributed variable which typically is stored on the nodes.\hypertarget{classcsmp_1_1_two_phase_implicit_node_centered_f_v_transport_design}{}\doxysubsection{\texorpdfstring{Design Intent}{Design Intent}}\label{classcsmp_1_1_two_phase_implicit_node_centered_f_v_transport_design}
The \doxylink{classcsmp_1_1_element}{Element} class is a structural object that forms part of a Bridge design pattern (pattern 151, Gamma et al. 1995). The bridge pattern is used to allow that elements can be mass-\/contructed by a container class (an STL vector in the \doxylink{classcsmp_1_1_mesh_manager}{Mesh\+Manager}), but that they have polymorphic properties at the same. time. Also a mesh usually has many elements, but only a few element types. This is achieved by "{}bridging"{} the \doxylink{classcsmp_1_1_element}{Element} objects to a few \doxylink{classcsmp_1_1_finite_element}{Finite\+Element} object pointers stored in the global array global\+FE\+\_\+types\mbox{[}\mbox{]}.

A class diagram of the Element-\/\+Finite\+Element bridge pattern is shown in the CSP3D User Guide in the developers section.\hypertarget{classcsmp_1_1_o_d_e___stiff_solver_Applicability}{}\doxysubsection{\texorpdfstring{Applicability}{Applicability}}\label{classcsmp_1_1_o_d_e___stiff_solver_Applicability}
The \doxylink{classcsmp_1_1_element}{Element} class should be applicable in any type of finite-\/element computation. Higher-\/order elements will make use of the ability to store retrieve integration point data.\hypertarget{classcsmp_1_1_v_data_structure}{}\doxysubsection{\texorpdfstring{Structure}{Structure}}\label{classcsmp_1_1_v_data_structure}
The structure of the \doxylink{classcsmp_1_1_element}{Element} -\/ \doxylink{classcsmp_1_1_finite_element}{Finite\+Element} bridge pattern is described in Gamma et al. 1995 (p. 151). The element interface is broken down into a part that echoes the interfaces of the \doxylink{classcsmp_1_1_finite_element}{Finite\+Element} base class from which the desired element types are inherited thereby giving these inter-\/ faces polymorphic behaviour.

The main operations which the element is used for are the retrieval of property values, node coordinate matrices, and node ID number vectors which are used in the assembly of the element equations. The element matrices are square and theur size is equivalent to the product of the degrees of freedom of each node and the number of nodes.\hypertarget{classcsmp_1_1_element_partcipants}{}\doxysubsection{\texorpdfstring{Participants}{Participants}}\label{classcsmp_1_1_element_partcipants}
The \doxylink{classcsmp_1_1_element}{Element} queries Nodes, Integration\+Points, and the Memory\+Manager$<$dim$>$ to obtain the data which it needs in its computations. It cannot exist without reference to the \doxylink{classcsmp_1_1_finite_element}{Finite\+Element} which implements half of its interface.

The \doxylink{classcsmp_1_1_element}{Element} uses \doxylink{classcsmp_1_1_dense_matrix}{Dense\+Matrix$<$\+DM\+\_\+\+MIN$>$}, and STL vector objects to receive and tranfer data.\hypertarget{classcsmp_1_1_time_step_evaluator_collaborations}{}\doxysubsection{\texorpdfstring{Collaborations}{Collaborations}}\label{classcsmp_1_1_time_step_evaluator_collaborations}
Elements can collaborate with \doxylink{classcsmp_1_1_visitor}{Visitor} objects through their \doxylink{classcsmp_1_1_element_aa81a196f4cdd443d0e75b7b1de514d94}{Accept()} interface. This combines the methods of the \doxylink{classcsmp_1_1_visitor}{Visitor} with the functionality of the \doxylink{classcsmp_1_1_element}{Element}.

The main collaboration exists between Elements and Algorithms. The latter query the \doxylink{classcsmp_1_1_element}{Element} for coordinate and property matrices and a node number vector. The new Algorithm class queries Elements through virtual methods of the Math\+Operator base classes.\hypertarget{classcsmp_1_1_two_phase_implicit_node_centered_f_v_transport_consequences}{}\doxysubsection{\texorpdfstring{Consequences}{Consequences}}\label{classcsmp_1_1_two_phase_implicit_node_centered_f_v_transport_consequences}
Elements are "{}finite-\/element-\/independent"{} mesh-\/building blocks. Because variables are only accessed through the Elements but not stored there, the mesh storage is also independent from the number of properties associated with it, while encapsulation is maintained and the access hierarchy is preserved.\hypertarget{namespacecsmp_implementation}{}\doxysubsection{\texorpdfstring{Implementation}{Implementation}}\label{namespacecsmp_implementation}
The bridge between the \doxylink{classcsmp_1_1_element}{Element} and the \doxylink{classcsmp_1_1_finite_element}{Finite\+Element} is implemented as a reference. It is initialized either through the default constructor which accesses the global\+FE\+\_\+types\mbox{[}\mbox{]} array, or, through a constructor which takes a reference to a finite element as argument.

Nodes, Integration\+Points, and Neighbors of an \doxylink{classcsmp_1_1_element}{Element} are accessed by pointers which are initialized through the Connect\+To...() interfaces. Methods with the same name interface the \doxylink{classcsmp_1_1_element}{Element} with the methods of the \doxylink{classcsmp_1_1_finite_element}{Finite\+Element}. The \doxylink{classcsmp_1_1_element}{Element} methods \doxylink{classcsmp_1_1_local_variable_storage_a4387c2c28afd79c9142834fc4a976b48}{Read()}, \doxylink{classcsmp_1_1_local_variable_storage_a8642fe6f83bb6981e7c0d6ab5b2c0248}{Store()} and \doxylink{classcsmp_1_1_local_variable_storage_a13c8a3dae3a8ba916f712f7e96d000d1}{Status()} are used to access element properties. Alternatively, to property output into \doxylink{classcsmp_1_1_dense_matrix}{Dense\+Matrix$<$\+DM\+\_\+\+MIN$>$} and vector objects you can also get STL vectors of scalar, vector, and tensor properties.\hypertarget{group___c_s_m_pglobal_enums_application}{}\doxysubsection{\texorpdfstring{Application Examples}{Application Examples}}\label{group___c_s_m_pglobal_enums_application}
The Visit(\+Element\texorpdfstring{$\ast$}{*} e) method in "{}\+Transport\+Visitor.\+h"{} illustrates nicely the functionality of the \doxylink{classcsmp_1_1_element}{Element} class. In this method element and node properties and node property averages are obtained and written back to the mesh.\hypertarget{classcsmp_1_1_element_IMPORTANT}{}\doxysubsection{\texorpdfstring{-\/ FOR DEVELOPERS}{-\/ FOR DEVELOPERS}}\label{classcsmp_1_1_element_IMPORTANT}
Consider that users of the policies may also want to work on other incarnations of the \doxylink{classcsmp_1_1_element}{Element}, in particular ones with less policies. This only works when the policies only depend on the functionality of the element, but not on each other!

As a key difference between policies and traits, the latter have state. Thus, the finite-\/element policy own the fe pointer and the fv policy ons the fv pointer which is key to the design.

For the current design, however, this is only partially true because the \doxylink{classcsmp_1_1_finite_volume_policy}{Finite\+Volume\+Policy} depends on finite element functionality. Thus, one can have an element with FEM but without FVM, but not vice versa.
